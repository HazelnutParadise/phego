PHP 8.5.12 參考案例確認的收尾行為包含：一般 fatal error 禁止當時既存物件再解構，之後新建物件仍可正常解構；未捕捉 Throwable 允許 shutdown 與解構。shutdown 內 exit 可改退出碼，但不解除先前 fatal 對既存物件的標記。[frame_locals.php](../../tests/lifecycle/w14/frame_locals.php) 中先建立 `$a`、再建立 `$b`，兩個固定平台都先解構 `local-a`、再解構 `local-b`。Go 核心依 `local(&slot)` 登記位置的先後順序釋放目前值，不採物件建立時間或反向堆疊順序；VM adapter 仍須依精確 PHP 版本安排登記。第一個解構拋例外後仍完成其餘局部值的 unwind。最內層輸出 handler 拋例外會停止剩餘 flush。handler 正常回傳時，它自己的 echo 會被丟棄並產生棄用診斷。handler 執行期間，它的緩衝和 PHP 一樣留在堆疊上：`ob_get_level()` 會算到它，handler 的 echo（包括它的區域變數解構時的輸出）直接接在這個緩衝後面並計入輸出上限。handler 正常回傳後，即使區域變數的解構再拋出例外或呼叫 exit，PHP 仍使用回傳值並發出棄用訊息（`solo_return_dtor_throw` 輸出 `<Rcaught:dtor|after>`，`solo_return_dtor_exit` 輸出 `<RS>`、退出碼 4），因為 main/output.c 只看回傳值是否存在；請求結束時則同樣全部丟棄（`solo_shutdown_return_dtor_exit`）。handler 本身拋出例外或呼叫 exit 時沒有回傳值：從 PHP 程式呼叫 `ob_end_flush()` 這類函式時，原緩衝連同它的 echo 一起交給下一層，不發棄用訊息，例外或 exit 再傳回呼叫端（`solo_end_exit` 輸出 `[bodyxS]`、退出碼 3）。請求結束時的 flush 沒有 PHP frame，PHP 會直接跳出 `php_output_end_all`，所有緩衝都被丟棄，外層 handler 不再執行；例外回報為未捕捉，exit 保留退出碼（`solo_shutdown_throw`、`solo_shutdown_exit` 都沒有輸出）。棄用訊息只在 handler 有回傳值、而且執行期間有寫入時產生，零長度的 `printf("")` 也算（`solo_printf_empty`）；handler 因 fatal、exit、例外或 Phego 上限而中止時不發（`solo_end_lock_echo` 只有 fatal）。handler 本身或它的區域變數解構發生 fatal 時，PHP 會直接跳出，緩衝留在堆疊上、輸出層仍標記為執行中：shutdown function 看到的 `ob_get_level()` 包含它，請求結束時的 flush 再觸發 `PHP Request Shutdown: Cannot use output buffering in output buffering display handlers`，最後什麼都不印（`solo_handler_fatal`、`solo_return_dtor_fatal`）。handler 內呼叫 `ob_start()`、`ob_end_flush()` 這類緩衝操作會造成 fatal，訊息帶呼叫的函式名稱，例如 `ob_end_flush(): Cannot use output buffering in output buffering display handlers`。所有緩衝當場丟棄而不執行外層 handler，之後的輸出直接寫出（`buffer_nested_start_shutdown`、`buffer_nested_start_flush`）。`endBuffer(op)` 提供 `ob_end_flush()` 這類函式的單層結束。handler 輸出造成的棄用訊息帶 handler 的 PHP 可呼叫名稱（`startBuffer(name, filter)` 的 `name`，例如 `{closure:FILE:LINE}`）與觸發 flush 的情境：一般是當下的函式名稱（`ob_end_flush():`、`ob_get_clean():`，chunk 觸發時是作用中的使用者函式），請求結束時是 `PHP Request Shutdown:`。固定映像實測 `ob_end_clean()` 與 `ob_get_clean()` 也會呼叫 handler 並發出同一則棄用訊息，W-17 接上這些函式時須走 `endBuffer` 路徑。handler 回傳 false 時，PHP 也把原緩衝加上 echo 交給下一層，但會發棄用訊息。緩衝操作造成 fatal 後輸出已停用，之後再呼叫 `ob_start()` 會回傳 false 並發出 `ob_start(): Failed to create buffer` Notice。`outputFilter` 與 `startBuffer` 目前都沒有表達 PHP false 的方式，W-17 接上 ob_* 函式時要一併決定。W-17 另須處理固定映像已確認的行為：`printf("")` 要呼叫零長度的寫入，`echo ""` 則不寫出；handler 回傳物件時，PHP 先解構區域變數、再判斷棄用、最後才把回傳值轉成字串，`__toString` 內的 echo 不觸發棄用，`__toString` 拋例外時發棄用、不傳出任何內容並把例外交給呼叫端，所以 `outputFilter` 要能回報「回傳了什麼」，轉換放在 filter 之後；請求結束時 handler 拋出的例外若有 `set_exception_handler`，PHP 會呼叫它而不中止 flush（輸出 `bodyxH`）。參考重播除了事件順序，也比對每個診斷的等級及它在事件之間的位置，並逐字比對 handler 的棄用訊息與緩衝操作 fatal 的訊息。輸出 handler 執行時 heap 仍可用，handler 留存到最後的物件不再得到第二輪 shutdown 解構。

### display_errors 與 log_errors

PHP 的每個診斷都經過 `report()`，行為和 `php_error_cb` 相同：開 log_errors 時把一份記在 diagnostics，開 display_errors 時把顯示文字交給 `write()`，所以顯示的錯誤會進入目前的 ob 緩衝並經過 handler。預設只開 log，和改動前一樣。顯示文字的位置與 stack trace 由 VM 透過 `errorChannels.text` 提供，runtime 只決定文字送到哪裡；沒有提供時用 PHP 在沒有作用中檔案時的 `Unknown`、第 0 行。

依 PHP 8.5.12 的 main/output.c，有三個規則必須照做：

- handler 執行期間的任何寫入，都會讓接收它的緩衝被標成「有輸出」。handler 自己的 echo 和 handler 內發出的 Warning 都寫進自己的緩衝，事後被丟棄並觸發棄用訊息（`solo_display_handler`）。
- handler 的棄用訊息是在該 handler 被停用後才發出，所以它的顯示文字跳過這個 handler，寫進下一層緩衝。這時 PHP 仍標記有 handler 在執行，下一層也因此被標成有輸出，flush 時再發一則棄用訊息。三層緩衝在請求結束時就會出現三則（`buffer_echo` 的 display 輸出）。
- 請求結束的 flush 中 handler 拋出例外時，未捕捉例外的顯示文字寫進正在執行的緩衝，隨即和所有緩衝一起被丟棄，所以什麼都不印。

`solo_display_upper` 驗證 handler 會改寫顯示的錯誤：`ob_start(fn($s) => strtoupper($s))` 下，Warning、Deprecated 與 Fatal error 的文字都變成大寫。`ob_start('strtoupper')` 不能這樣用：PHP 呼叫 handler 時傳兩個參數，`strtoupper()` 只收一個，結果是 `ArgumentCountError`，什麼都不輸出。

參考資料對每個 fixture 各跑一次 `display_errors=stderr` 與 `display_errors=1 log_errors=1`。重播在兩種模式下都要求 stdout 逐位元組相同、退出碼相同，並比對 log 的等級順序與事件的相對位置。display 模式的顯示文字取自 PHP 的 log 紀錄，同時檢查每一則都是 PHP 在那個時點發出的同一個診斷。W-17 要把 display_errors、log_errors、html_errors 與 error_log 接到 INI，並提供含位置與 stack trace 的 `text`。

管理者取消、輸出 writer 失敗及內部錯誤會停止後續 PHP callback，保留已接受的輸出，只執行 Runtime 清理。這是宿主停止契約，不冒充 PHP 正常 shutdown。writer 接受位元組不代表資料已送達客戶端。清理錯誤與 PHP 最終結束原因分開保存；逾時只代表呼叫者停止等待，背景清理可能仍在進行，回傳快照不會被事後改寫。

後續審查再修正 [exit 被聚合清理的較早例外蓋掉](https://github.com/HazelnutParadise/phego/pull/74#discussion_r4436446851)與 [exit 時函式區域值清理太晚](https://github.com/HazelnutParadise/phego/pull/74#discussion_r4436446856)。退出時先清理函式區域值，再執行 shutdown，仍略過 finally。結束原因保留實際發生順序，已捕捉的例外不會重新傳播；最後退出碼另行保留。新增七個 PHP 對照案例，總數增為各 37 案，涵蓋 exit／throw 先後、多次 exit 與清理 callback 自行捕捉例外，詳見 [exit 審查回歸證據](evidence/W-14-exit-review.json)。

最新審查修正[連續解構例外遺失後續例外](https://github.com/HazelnutParadise/phego/pull/74#discussion_r4436538835)與[局部陣列修改後釋放錯誤的值](https://github.com/HazelnutParadise/phego/pull/74#discussion_r4436538841)。連續例外保留最後一個例外及完整前因，已捕捉的中間例外不加入鏈中。frame 改為登記變數位置，離開時釋放該位置的目前值，避免複製後修改陣列時誤釋放全域共用的舊值。新增六個 PHP 對照案例，總數為各 43 案，詳見[局部變數與例外鏈證據](evidence/W-14-slots-review.json)。

內部 `local(&slot)` 為尚未持有邏輯所有權的位置建立所有權，必須在 `assign`、`bind` 或陣列修改前登記。登記後透過 heap 操作修改，不能以 Go 賦值直接替換。nil 或已在任一有效 frame 登記的位置會被拒絕，避免重複保留與釋放。

`tryCatch(body, selector)` 在同一個 PHP frame 內處理例外，selector 為符合類別的 Throwable 選擇 handler，回傳 nil 則繼續傳播。進入 handler 前恢復 try 範圍外原本尚未處理的結束狀態，避免已捕捉的例外被誤接到後續新例外。VM adapter 模擬 catch 後繼續執行時須使用此入口，不能只忽略 Go 回傳的 throw。exit、fatal 與宿主停止不會進入 handler，最後退出碼也不會被清除。三個參考案例分別驗證 catch 後直接 throw、再呼叫函式、以及解構物件時的新例外。

[finally return 抑制例外後殘留前因](https://github.com/HazelnutParadise/phego/pull/74#discussion_r4436623846)已修正：當 finally 的回傳取代本函式的 throw，先恢復外層尚未處理的狀態，再清理回傳值與局部值。新增三個參考案例，分別涵蓋一般回傳、外層既有例外、以及呼叫者使用回傳物件的情境，總數為各 46 案。正常結束或拋例外的 finally 保留原本例外傳播規則，詳見[finally 審查回歸證據](evidence/W-14-finally-review.json)。
