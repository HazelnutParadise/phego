# Complete historical PHP compatibility

The target includes every publicly released PHP generation from the first PHP Tools onward. It is not limited to PHP 5, 7, or 8. Exact release identities and patch-level behavior must be preserved, with separate entries for public prereleases and historical experimental snapshots.

PHP Tools, FI, Construction Kit, and PHP/FI require their own historical syntax and tool behavior. A modern parser with a version number switch is not sufficient. The official history and archives are starting evidence, not a completed release inventory. In particular, an available PHP 1.08 archive does not establish that the first public release has been recovered.

Use immutable language profiles that specify exact release, language generation, guest integer/platform semantics, modules, configuration behavior, security differences, and data versions. Keep those profiles in compilation, runtime, cache, and native artifact identity.

Known engine memory corruption and permission escapes are not compatibility features. Deliberate historical language behavior and security-policy restrictions must be distinguished. A policy denial that prevents a normal historical workflow must be reported, not counted as transparent compatibility.

The [history policy](../data/php-history-policy.json) is a planning catalog, not a list of certified releases. Build the exact source inventory and isolated reference environments under W-49. The current, still incomplete, [release inventory](php-release-inventory.json) lists one record per discovered release with its source and evidence status. Never fabricate checksums, substitute an adjacent version, or remove an unavailable historical release from the goal.

Required evidence includes source identity, license, build environment, matching oracle, semantic tests, applicable real applications, and documented security differences. Unknowns and unavailable evidence remain completion blockers.

The authoritative behavior contract is in [specification chapters 36 and 40](../spec/specification.zh-TW.md#chapter-36). Background sources are the [official history](https://www.php.net/manual/en/history.php.php), [PHP 1 archive](https://museum.php.net/php1/), and [PHP/FI 2 manual](https://www.php.net/manual/phpfi2.php).

## Upstream update review

Use `python3 tools/upstream_update.py --help` for the source-verified update entry point on Unix platforms supporting safe `O_NONBLOCK`/`O_NOFOLLOW` file reads. Other platforms return an explicit unsupported-input diagnostic. `pair --lock LOCK OLD_ARCHIVE NEW_ARCHIVE` accepts the reviewed old/new identities in a W-02 comparison report. Both archives must match their locked SHA-256 values before decoding. The output preserves the detailed stub, grammar, PHPT and security classification and lists every changed regular file with its hashes and responsible work packages. Implementation and unclassified changes require behavior regression even when the signatures match. Raw stub changes also remain visible when the declaration parser cannot interpret them.

`watch BASELINE OBSERVED` consumes W-02 observation snapshots and downloads only changed release/digest pairs from php.net. `--archive-dir DIR` uses an offline cache named `<sha256>.tar.xz` and never downloads a missing entry. Added or removed series, missing archives and verification failures remain blocked in the output. Metadata-only changes still require review. The existing daily upstream-watch workflow retains both the observation and the classified report, including partial failures.

Online archive downloads use a 180-second POSIX timer covering connection setup, HTTP headers, chunk framing and body reads, alongside a 30-second socket timeout. They require the main thread with no active timer. Unsupported contexts remain blocked and may use `--archive-dir`; the tool does not replace a caller's active timer. HTTP protocol errors also produce per-series blocked records. Valid chunked downloads remain supported.

Added and modified PHPT files become `pending` regression candidates bound to the exact release, source archive, path and raw PHPT hash. Maintainers must run them through W-04 against the corresponding Phego profile before accepting compatibility. The classifier never executes downloaded source or tests. Its `compatibility: not_assessed` field applies even to empty differences. The current tool acceptance and downstream blockers are recorded in [W-45 evidence](../implementation/evidence/W-45.json).

## Vulnerability catalog

[`php-cve-catalog.json`](php-cve-catalog.json) lists every CVE that NVD files against `cpe:2.3:a:php:php`, every CVE or GHSA advisory that the php.net ChangeLogs for PHP 4, 5, 7 and 8 name, and every security advisory php-src publishes on GitHub, which also maps each GHSA to its CVE. Each entry carries its source text, the Phego component and work package that must handle the trigger, a defect class, the php-src 8.5.12 tests named after its bug numbers, and a status: `tested` (a case in [tests/security/php-cve](../../tests/security/php-cve/README.md) passes), `pending` (the component is not built yet), `not-provided` (an in-server SAPI module Phego does not ship) or `excluded` (the defect is not in PHP itself). This is W-41 step 2 (REQ-067; T-133, T-134), started early so the cases grow as each package lands.

`tools/php_cve_catalog.py fetch --cache DIR` downloads the sources and lists the pinned image's source archive. `build --cache DIR` classifies them with the rules in the tool, applies the reviewed entries in [`php-cve-triage.json`](php-cve-triage.json) and regenerates the vulnerability section of the repository README. `check` repeats the classification offline from the committed catalog and fails when the catalog, the cases, `security-assessments.json` or the README disagree, when an identifier a source yielded is missing from the catalog, or when an entry has no triage record. A new upstream advisory therefore needs a refetch, a triage record and a build before `check` passes. An entry still pending in a component the engine already runs must say in its note what its case waits for.

A vulnerability fixed after the pinned release (8.5.13 fixed several, including CVE-2026-128064) still exists in PHP 8.5.12, so its case cannot take PHP 8.5.12's output as the expectation. `build` requires its triage note to state the behaviour the fix requires and refuses a case for it until the reference images move to a fixed release.

Known gaps: NVD returns only records it has analysed with a php:php CPE, so a new PHP CVE that NVD has not analysed and no ChangeLog or php-src advisory names yet is missing until one of them lists it; on 2026-11-22 all 83 php-src advisories were present. Security fixes from before CVE numbering that carry no identifier are not catalogued. Writing the first cases also showed that a plain function recursing without end grows host memory without bound under the default `Limits`, where PHP stops at `memory_limit`; CVE-2006-1549 tracks it for the memory metering of W-20.
