# W-20｜宿主可以限制每次 PHP 執行的資源與外部能力

規格工作包：能力與配額核心。階段：M2。負責角色：安全Runtime維護者。

實作狀態：能力檢查、檔案掛載、網路目的地檢查、資源計量、接納上限與公開的政策設定及錯誤型別已實作，執行期入口要等 VM 與各功能工作包接上，正式工作包驗收待確認。驗收狀態：`not_run`。沒有可執行 PHP 引擎。

## 實作與測試位置

內部的能力與計量在 `internal/policy/`：`policy.go` 是能力集合與模式，`files.go` 是檔案掛載，`files_root.go` 是主機目錄的共用讀寫路徑解析、實體保護與硬連結檢查，`files_absolute.go` 負責絕對連結的掛載換算，`files_open_unix.go`／`files_open_other.go` 提供各平台開啟旗標，`files_fs.go` 是可信任 FS 來源的路徑與虛擬掛載處理，`network.go` 是網路目的地檢查，`meter.go` 是每次執行的計量，`admission.go` 是 Engine 層的接納上限，`audit.go` 是有上限的稽核紀錄，測試在 `policy_test.go`、`review_test.go` 與 `overlap_test.go`。公開設定在根套件的 `policy.go`（`Policy`、`FileGrant`、`NetworkGrant`、`Limits` 與常數），錯誤型別在 `errors.go`（`PolicyError`、`ResourceError`），`engine.go` 的 `NewEngine`、`Run`、`RunFile` 與 `Close` 已接上，測試在 `policy_test.go`，用法範例在 `example_test.go` 的 `ExampleConfig_policy`。

## 能力與配額設計

`Config.Policy` 的零值不授權任何東西。`NewEngine` 驗證整份設定後，轉成內部的不可變政策，同一個 Engine 的每次執行都問同一份政策。驗證失敗時回傳 `ConfigError`，欄位用公開路徑命名，例如 `Policy.Files[0].Path`，Engine 也不會建立一半。模式只影響規則事件：`ModeEnforce` 會擋下符合規則的操作，`ModeCompat` 與 `ModeObserve` 只記錄。未授權的能力在三種模式下都會被拒絕。

檔案以掛載方式授權。每個 `FileGrant` 把 PHP 看到的絕對路徑對應到一個宿主目錄或一個唯讀 `fs.FS`。路徑落在多個掛載時，用最長的那個。宿主檔案經 `os.Root` 開啟並核對實體身分。相對符號連結不能越出來源根。絕對符號連結可轉入另一個已授權 Root，轉換後的連結片段不能以 `..` 離開目標掛載。請求路徑中的 `..` 則依明確掛載的虛擬父目錄解析。寫入要求掛載設定 `Write`。只有舊 `Config.Files` 而沒有 `Policy.Files` 時，`RunFile` 保留原樣呼叫 `Files.Open(path)`，不清理或改寫路徑，並保留檔案系統回傳的錯誤。兩者混用時，舊 `Files` 為 `/` 的唯讀掛載，明確的較長掛載優先，拒絕或讀取失敗不回退。

網路授權比對 scheme、主機（可用 `*.example.com`）與連接埠。建立 socket 時再檢查實際連上的 IP，所以授權的名稱解析到內網、loopback、link-local 或保留位址時一律拒絕，除非該授權設了 `AllowPrivate`。轉址與 proxy 要在 W-32 的 HTTP 用戶端重新檢查。

`Limits` 是每次執行的邏輯預算：步數、值的邏輯大小、輸出、診斷數、呼叫深度、同時開檔、同時連線，以及 include 與 eval 的累計編譯量。這些是引擎計量的數字，不是程序的 RSS。超過預算或加總會溢位時拒絕，而且被拒絕的那次不會算進用量。`Checkpoint` 讓迴圈、呼叫與長操作在同一個位置檢查取消與步數。`MaxActive > 0` 時，接納器限制同時執行與排隊的數量，兩者都滿時在開始前回傳 `ResourceError`。`MaxActive == 0` 不設接納上限，且 `MaxQueued` 必須為零。HTTP 接納與 body 緩衝仍待下游整合。`Close` 停止接納新工作、喚醒排隊者並等待既有工作，等待受傳入的 context 限制。目前不會取消已開始的工作，執行中的取消仍待 VM 整合。之後的新工作回傳 `ErrEngineClosed`。

稽核紀錄有固定上限，滿了只計數不再保存，網址中的帳密與查詢參數在保存前就遮蔽。

## 重疊目錄的寫入保護

REQ-033、REQ-037、REQ-059 的局部回歸對應 T-065、T-066、T-073、T-074、T-117、T-118。使用者要求保留父目錄可寫、子目錄唯讀的設定，保護實際檔案，而非只提醒使用者避免重疊。

`files_root.go` 逐個解析路徑元件，以目錄 handle 固定父目錄，並核對開啟前後的實體身分。相對符號連結展開後重新選擇掛載，最長唯讀掛載仍會拒絕寫入。不同虛擬名稱指向相同實體樹，也不能避開保護。實體包含關係使用 `SameFile` 核對祖先目錄，不依路徑大小寫或字串前綴判斷。

保護範圍包含唯讀掛載本身，以及被唯讀／FS 掛載遮蔽的父目錄底層資料。明確、更長的可寫子掛載可以寫入自己的後端，不會同時解鎖被遮蔽的其他資料。同一個實體根有衝突授權時，唯讀保護優先。

已存在的檔案先以不會建立或截斷的方式開啟，核對身分後才允許截斷或交出可寫 handle。新檔以獨占建立，避免最後一個路徑元件在檢查後被換成符號連結。多硬連結或平台無法提供連結數時，掃描受保護樹並比較實體檔案身分；合法、沒有連到唯讀資料的硬連結仍可寫入。

路徑深度與祖先查找上限為 256，符號連結及跨掛載重新解析各上限 40。硬連結檢查每棵受保護樹最多檢查 100,000 個項目，深度上限 256，每次目錄讀取 128 個項目。無法查驗、身分變動或超過檢查上限時拒絕寫入，不把未知視為允許。一般單硬連結檔案不需要掃描整棵樹。

測試位於 `internal/policy/overlap_test.go`：

| 實際輸入 | 修正前 | 修正後 |
|---|---|---|
| 中途／最終符號連結指向唯讀目錄或其子目錄 | 可開啟或截斷 | 拒絕，原內容不變且不能建立新檔 |
| 不同虛擬掛載指向同一唯讀實體樹，包含可寫掛載直接起於其子目錄 | 可改寫 | 拒絕 |
| 不分大小寫的磁碟上，以另一種大小寫設定可寫別名 | 可截斷唯讀檔案 | 按實體祖先關係拒絕 |
| 硬連結連到唯讀檔案或被 FS 掛載遮蔽的底層檔案 | 可截斷 | 拒絕 |
| 符號連結在可寫與唯讀目標間反覆交換 | 原路徑可繞過 | 不改動唯讀內容 |
| 合法可寫別名、無唯讀目標的硬連結、更長的可寫子掛載 | 可使用 | 保持可使用 |

以上範圍沿用規格 10.1 的可信任宿主模型：目前內部政策層的檔案操作入口只有 `OpenFile`，沒有搬移目錄或建立連結的入口；PHP 執行引擎仍未完成。宿主 Go 程式直接更動受保護樹、掛載拓樸、裝置或檔案系統邊界，不屬於 PHP 能力隔離可攔截的操作。新增 rename／link 等入口時，必須共用保護並重新驗證；這不是 OS 沙箱或任意宿主檔案系統變更的保證。使用者已確認：`FS` 是可信任的宿主讀取介面，實作必須自行限制讀取範圍及副作用，不能把任意 `FS.Open` 當成自動受隔離的程式。磁碟目錄必須使用 `Root`；`os.DirFS` 會跟隨逃出目錄的符號連結，不符合這項契約。Phego 驗證公開掛載路徑與設定結構，但無法查驗任意 Go 實作內部如何存取資料。舊 `Config.Files` 保留原有路徑及錯誤行為，不新增未曾提供的 OS 隔離保證。

本輪實作／測試提交為 `caabf0d`／`3a5eaac`，環境為 Go 1.26.5、Darwin arm64。`CGO_ENABLED=0 go test -race ./...`、`go vet ./...`、`gofmt -l .` 及文件驗證通過，Windows amd64 的政策套件交叉編譯通過，但沒有執行 Windows 測試。大小寫別名案例在本輪 Mac 實際通過，在區分大小寫的檔案系統才依環境不適用跳過。指令、退出碼與原始輸出記錄於[本輪局部驗證](evidence/W-20-overlap-local.json)，完整產品情境維持 `not_run`。

讀取也使用 `files_root.go` 的解析與掛載重選：透過符號連結或大小寫別名到達內層掛載時，會讀取該掛載的後端，不讀取被遮蔽的父目錄檔案。硬連結沒有可重新解析的目標字串，因此另外檢查是否指向被遮蔽的實體資料。一般可讀硬連結與相同後端的掛載仍能使用。`TestReviewRunFileDoesNotReadShadowedAlias` 在 `f721786` 的隔離原始碼副本中實際失敗，因為別名讀到了隱藏來源並產生 PHP ParseError；修正後只看得到選定掛載。實作／測試提交為 `4a742b9`／`f4ced99`，實際命令及結果見[讀取別名驗證](evidence/W-20-read-alias-local.json)。

前次審查回歸另修正 IPv6 介面名稱大小寫與非公開位址分類：`fe80::1%En0` 不再授權不同的 `%en0`，`fec0::/10` 及舊 IPv4-compatible `::/96` 不再視為公開位址，IPv4 映射的合法公開位址仍可使用。`TestNetworkIPv6ZoneNamesRemainCaseSensitive` 與 `TestPublicRefusesDeprecatedIPv6LocalRanges` 在修正前實際失敗，修正後通過。

使用者另核准有重疊掛載的 `FS` 所開啟的目錄必須實作 `fs.ReadDirFile`，列舉名稱須與 `Open` 的精確名稱語意一致。引擎拒絕 `/Protected` 等未列出的大小寫別名，也拒絕無法查驗的來源；單獨使用的 `FS`，以及沒有設定 `Policy.Files` 的舊 `Config.Files`，不增加此要求。使用者另已核准：舊 `Files` 與新掛載混用時，作為父來源的舊 `Files` 也必須提供可查驗的目錄列舉，無法查驗就拒絕讀取。每次 FS 路徑解析最多列舉 100,000 筆，每批 128 筆，跨掛載重入最多 40 次，各次解析重新計算列舉預算。只用於到達下層掛載的虛擬祖先不能回落讀取未驗證的父來源。唯讀父目錄的符號連結可轉入明確可寫的子掛載，仍不能寫入被遮蔽的舊資料。相關案例位於 `TestFSMountsRejectUnlistedCaseAliases`、`TestFSMountsRequireBoundedDirectoryEnumeration`、`TestFSVirtualAncestorsDoNotEnableCaseAliases` 與 `TestReadOnlyParentsResolveWritableChildAliases`，皆有修正前失敗證據。該次命令及原始結果見[前次審查局部驗證](evidence/W-20-latest-review-local.json)。


後續巢狀連結回歸以私有路徑元件保留每段連結的來源根，跨掛載時不丟掉該限制。`deep -> sub/deep`、`link -> deep/../../file` 可正確讀到根內檔案，連結中的 `..` 仍不能越出來源根。被子掛載遮蔽且已確認越出父 Root 的舊連結，不再阻擋無關檔案；一般讀取、硬連結讀取與寫入共用這個判斷。權限或 I/O 錯誤仍拒絕操作。Go 尚未公開 Root 越界錯誤的可比對值，實作精確比對目前的錯誤文字；未來未知錯誤仍視為失敗。

有下層掛載的 `FS` 若未提供 `fs.ReadLinkFS`，所有來源路徑元件都需查驗目錄項目，列出的符號連結一律拒絕，避免最後的 `Open` 跟隨連結繞過遮蔽。一般檔案與沒有重疊掛載的舊來源維持原行為。`TestReviewLegacyFilesMixedMountsRequireVerifiableDirectories` 從公開 `RunFile` 驗證舊來源單獨使用、混用時拒絕不可查驗來源，以及可查驗來源保留子掛載遮蔽，結果見[舊來源混用驗證](evidence/W-20-legacy-mixed-local.json)。`TestSymlinkTargetsResolveNestedLinksBeforeParents`、`TestShadowedEscapingSymlinkDoesNotBlockOtherDirectories`、`TestOverlappingFSRejectsUnresolvableSymlinks` 有修正前失敗證據，`TestSymlinkBoundariesSurviveMountRemapping` 另驗證跨 Root／FS 的合法與越界對照。命令與結果見[巢狀連結最終驗證](evidence/W-20-nested-symlink-local.json)。


重疊的磁碟來源必須使用 `Root`。若 `FS` 有下層掛載，最終開檔後、交出檔案前會呼叫 `Stat`。可由 `os.SameFile(info, info)` 辨識為 OS 檔案資訊時，會關閉檔案並以 `PolicyError` 拒絕，要求改用具備實體別名檢查的 `Root`。`Stat` 失敗也會關閉檔案。這項查驗無法檢查任意 Go 包裝器的內部行為，不能從無法辨識的檔案資訊推論來源不接觸磁碟。可信任的宿主仍須保證來源符合契約。沒有下層掛載的既有 `Root.FS()`、舊 `Files` 單獨使用，以及`Sys` 帶有自訂資料的虛擬來源保留既有讀取行為。

`TestReviewOverlappingDiskFSRequiresRoot` 在 `b68d0fd` 的隔離副本中重現隱藏硬連結被交給 PHP 編譯器。同一實體資料改用 `Root` 時，硬連結拒絕且一般檔案仍可讀。修正後，重疊且可辨識的磁碟 `FS` 會在讀取前拒絕，合法 `Root`、單獨舊來源與虛擬來源控制維持通過，詳見[重疊磁碟來源驗證](evidence/W-20-os-fs-local.json)。本文現行契約與後續混用驗證，取代先前局部紀錄中未限定使用情境的「舊 Files 不變」描述。只有單獨使用才維持直接 `Open` 行為。

## 檔案來源的使用方式

磁碟資料夾使用 `FileGrant{Path: "/app", Root: "/srv/app"}`，讓 Phego 透過 `os.Root` 及共用的實體路徑檢查限制存取。宿主須控制既有硬連結，詳見下方實體限制。`ExampleFileGrant_root` 使用真實暫存目錄，驗證正常讀取與編譯，以及目錄外的拒絕結果。

程式內建檔案可用 `FS: embeddedFiles`。`FS` 的 Go 實作是可信任宿主程式，必須保證只讀取已授權資料；`ExampleConfig_policy` 使用不會存取磁碟的記憶體 FS 示範這種來源。不要以 `FS: os.DirFS(directory)` 代替安全目錄掛載。受控 `Root` 的外連符號連結拒絕測試與沒有下層掛載時的 `Root.FS()` 合法讀取測試，位於 `TestReviewRootAndRootFSConfineSymlinks`。

主機目錄路徑的 `..` 會在前面的符號連結解析完成後才處理。`link -> sub/deep` 時，`link/../file` 存取 `sub/file`，不會誤讀或截斷根目錄的 `file`。不存在的中間目錄、把一般檔案當目錄的 `file/.` 或 `file/` 都會失敗。掛載父路徑與只存在於虛擬來源中的掛載點另有合法控制測試。

前一輪整合的程式與測試提交為 `9798659`，已包含最新 `main` 的 W-45 變更。四項必要本機檢查均通過，額外工具測試為 466 項通過，Windows amd64 交叉編譯通過。完整命令、退出碼、原始輸出與限制保存於[最終局部驗證](evidence/W-20-final-local.json)。此紀錄取代先前兩份局部紀錄中的「FS 契約尚待決定」狀態，保留舊紀錄作當時證據。

`files_fs.go` 逐個處理 FS 的虛擬路徑元件，跨掛載時保留尚未解析的後綴；支援 `fs.ReadLinkFS` 的來源會先解析符號連結，再處理父目錄。非目錄與不存在的中間元件不能以 `..` 略過。沒有宿主同名目錄的多層虛擬掛載祖先也能走訪，但不能在沒有實體後端的祖先下建立檔案。

### FIFO 的相容差異與處理

在鎖定映像 `php@sha256:add6a138b6bd07edd645088917c081579f6e0d52d3c4361aff9d9309e6ebf9d9` 的 PHP 8.5.12 中實測：`fopen(FIFO, "r")` 無寫入端時由 2 秒外部期限終止（退出碼 124），延後 1 秒寫入 `payload` 則開啟成功並讀到內容（退出碼 0）。容器無網路、唯讀根目錄、移除 capabilities，限制 CPU、記憶體與程序數，只使用容器內暫存資料。上游 [plain_wrapper.c 的模式解析](https://github.com/php/php-src/blob/php-8.5.12/main/streams/plain_wrapper.c#L68-L109) 也顯示普通 `r` 不加非阻塞旗標。

`OpenFile` 沒有 context 參數，回傳 FIFO handle 會把阻塞問題移到後續讀取。因此採受控拒絕，這是明示的政策差異。Root 僅支援一般檔案與目錄。已知特殊檔案在開啟前拒絕，Unix 的實際開啟加 `O_NONBLOCK`，再核對身分與型別，避免檢查後被換成 FIFO。寫入與延後截斷使用同樣的非阻塞開啟保護。

`RunFile` 對 Root、FS 與單獨使用的舊 `Files` 都在讀取前確認一般檔案。FS 的非一般檔案回 `StatusFailed` 與 `fs.PathError`，已取得的檔案及名額都釋放。Root 的特殊檔案由政策層先回 `StatusPolicyDenied`。任意 FS 的 `Open`／`Stat` 是可信任宿主程式，這項修正不提供強制中斷宿主程式的能力。FIFO 測試使用 `syscall.Mkfifo`，因為 Go 的 `os` 套件沒有 `Mkfifo`，測試檔附 Unix 平台條件與逾時清理。

### 絕對符號連結與實體限制

Laravel 12.x 的 [StorageLinkCommand](https://github.com/laravel/framework/blob/18bf64aee02dda4efe172c0e3e940be94847b7db/src/Illuminate/Foundation/Console/StorageLinkCommand.php#L29-L60) 預設把 `public_path('storage')` 連到 `storage_path('app/public')`，只有 `--relative` 才使用相對連結。[Application](https://github.com/laravel/framework/blob/18bf64aee02dda4efe172c0e3e940be94847b7db/src/Illuminate/Foundation/Application.php#L560-L595) 由應用根目錄組成這些路徑，[Filesystem::link](https://github.com/laravel/framework/blob/18bf64aee02dda4efe172c0e3e940be94847b7db/src/Illuminate/Filesystem/Filesystem.php#L328-L339) 在 Unix 原樣把目標交給 `symlink`。一般以絕對應用根目錄啟動時，預設產生絕對連結。

Root 絕對目標只比對已授權 Dir 的完整路徑片段。掛載前綴經 `EvalSymlinks`，也識別設定中的 Dir 拼法，再選最長實體前綴。同一實體根有多個虛擬別名時優先目前掛載，其次是設定順序。剩餘片段保留原始 `..`、符號連結順序與結尾 `/`，帶著目標掛載限制進入既有解析器。重疊 Root 的讀寫保護繼續使用 `os.SameFile`。FS 的絕對符號連結維持拒絕。每次後端解析的連結上限與跨掛載重入上限各維持 40，並非全程合計 40 條連結。掛載拓樸由可信任宿主管理。

宿主預先建立的硬連結可以讓 Root 內的名稱指向目錄外相同 inode。`TestReviewFixRootHardlinkLimitation` 實測仍可讀到該內容，這是 `os.Root` 的限制。PHP 目前沒有建立連結的入口，未來 `link()` 必須檢查來源與目的都在授權內，不能只檢查目的路徑。

`*os.File.Name()` 與掛載目錄不存在時的底層錯誤可能含完整宿主路徑。這些值只供宿主診斷，未來 VM 的 `__FILE__` 與 PHP 可見訊息不得取用，必須使用 PHP 路徑。`TestReviewFixPolicyErrorTargetIsPHPPath` 驗證一般 `PolicyError.Target` 保持 PHP 路徑。

新增回歸位於 `internal/policy/*review_fixes_test.go`、`network_review_fixes_test.go`、`runfile_review_fixes_test.go` 與 `runfile_fifo_review_fixes_test.go`。本機實測平台為 Darwin arm64，PHP 參考測試為 Linux arm64 容器。Windows amd64 只做交叉編譯，沒有實跑，不能據此宣稱 Windows 的符號連結、裝置與競態防護已認證。

本輪原始失敗輸出、最終來源摘要與驗證結果見[網路與檔案修正驗證](evidence/W-20-review-fixes-local.json)。

本輪驗證命令與結果：`gofmt -l .` 無輸出，`CGO_ENABLED=0 go test -race ./...` 全部 7 個套件通過，`go vet ./...` 通過，`python3 tools/validate_docs.py` 的 34 項文件檢查通過，`GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go test -c ./internal/policy -o /tmp/phego-w20-policy-windows.test.exe` 成功。新增回歸先於修正執行並失敗，再以修正後的完整套件驗證。既有 `TestShadowedEscapingSymlinkDoesNotBlockOtherDirectories` 原本將逃逸目標同時授權為 `/shadow`，與新的跨掛載連結行為衝突，因此改用真正未授權的目錄，保留 `outside-root` 斷言。

## 相容、安全與範圍

維持 Go 單函式嵌入、預設不依賴 cgo／LLVM、第一版 PHP 起的全部歷史範圍、有界 goroutine、請求隔離與 Apache／Nginx FastCGI。任何後端都保留能力檢查及取消語意，正式執行不回退 Zend。
