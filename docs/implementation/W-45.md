## 差異分類

W-02 的 `tools/upstream_snapshot.py` 只記錄哪些語法、stub、測試與發行說明檔案的雜湊變了。`tools/upstream_diff.py` 讀出這些檔案的內容，說明變了什麼：

- **stub：** 從每個 `.stub.php` 取出函式、類別、介面、trait、enum、enum case、方法與常數的宣告，依命名空間補全名稱，比對新增、刪除與簽章改變。`const A = 1, B = 2;` 的每個常數各算一個宣告。同一個名稱在好幾個 stub 檔都有宣告時（例如 Apache 與 FPM 各自宣告 `apache_request_headers`），依檔案分開比對，改了其中一個也會報告。註解、doc comment 與 attribute 不算簽章，只改這些不會出現在報告裡。字串、heredoc 與 nowdoc 整段當成字串，裡面的文字不會被當成宣告，空白也照原樣比對。
- **條件編譯：** `#if`、`#ifdef`、`#elif`、`#else` 區塊裡的宣告，簽章前面會標出條件，例如 `[ifdef HAVE_PG_SERVICE] function pg_service(...)`。同一個名稱在不同分支各宣告一次時，每個分支的簽章都會保留並依檔案順序換行串接，任何一個分支改了都會報告成簽章改變。
- **語法：** 從 `zend_language_parser.y` 取出 token 與文法規則，比對增刪。
- **測試：** 列出新增、刪除與修改的 `.phpt`。`.phpt` 以原始位元組比對，不是 UTF-8 的位元組改了也算修改。
- **安全修補：** 從 NEWS 取出新版本中帶 GHSA 或 CVE 編號的條目。工具不判斷影響，每一筆都標成 `needs_assessment`。

每個變動依路徑或 NEWS 段落對應到負責的工作包，例如 `ext/pcre/` 與 PCRE 段落對應 W-30。對應不到的標成 `unmapped`，留給人工檢查，不會被丟掉。封存檔讀取沿用 W-02 的安全規則：限制大小、拒絕根目錄以外與含 `..` 的路徑。PAX 與 GNU 擴充標頭沿用 W-02 的上限，在配置記憶體之前就檢查。另外限制成員數（10 萬）、全部解壓縮的總量（512 MiB）與保留下來的文字總量（64 MiB），避免用很多個小壓縮成員撐大記憶體。8.5.12 實際是 27,730 個成員、解壓縮後 149 MB、保留 30.5 MB。

以 php.net 的 8.5.11 與 8.5.12 封存檔（SHA-256 與版本清冊一致）實際執行，6 秒內完成。報告列出 6 個新增函式、1 個刪除函式（`pg_service`，在 `#ifdef HAVE_PG_SERVICE` 區塊裡）、沒有簽章改變、沒有語法變動、測試新增 422 個、刪除 14 個、修改 37 個，以及 1 則安全修補。新增與刪除的函式和兩個版本 stub 檔的原始文字差異逐一核對過，結果一致。

## 安全審查回歸

PR #105 的後續安全審查確認兩項資源問題：XZ 解碼器會在 tar 成員檢查前配置 dictionary，巢狀條件則會在每個宣告前重複展開。新增的 `tools/test_upstream_diff_limits.py` 以實際封存檔及 stub 輸入重現，修正前有 14 個失敗斷言及 1 個串接 XZ 讀取錯誤，修正後 13 個測試全部通過，且已加入 W-03 manifest。

- W-02 與 W-45 共用 `tools/upstream_snapshot.py` 的封存檔入口，對 XZ 及 tarfile 原本辨識的 legacy LZMA 設定 128 MiB 解碼器記憶體上限。每次輸入及解碼輸出以 64 KiB 分塊，解碼總量另受檔案資料、標頭、成員對齊空間及 metadata 額度限制。解碼後只作原始 tar 解析，避免再次自動辨識壓縮格式。串接 XZ 的各個 stream 都套用相同上限，並在 tar 結束後檢查完整檔尾，拒絕截斷及無效尾端資料。
- stub 條件最多 128 層，當前條件文字與分隔符最多 64 KiB。每個 stub 的符號及簽章總量最多 8 MiB，跨 stub 的符號、路徑及簽章最多 64 MiB，皆以 UTF-8 位元組計算。先檢查總量才合併條件或簽章，同名宣告先保留片段，最後才合併，超額時明確報錯。

兩個官方封存檔的 dictionary 都需要超過 64 MiB，因此採 128 MiB 上限。修正後重新執行官方版本差異，報告逐位元組一致。340 位元組、宣告 1 GiB dictionary 的 XZ 輸入現在回報 `ValueError`，4,000 層條件的輸入也在產生簽章前被拒絕。正常 tar、gzip、bzip2、XZ 及既有 legacy LZMA 輸入均有回歸測試。

最終安全修正後，`python3 -m unittest discover -s tools -p 'test_*.py'` 的 466 個測試全部通過，相關套件的 81 個測試也全部通過。`CGO_ENABLED=0 go test ./...`、`CGO_ENABLED=0 go vet ./...` 與 34 項文件檢查均通過。tar 對齊空間的回歸另以 100 個 1-byte 成員驗證，確認合法邊界輸入不會被新的解碼額度誤拒。

後續 token 資源審查另補上每個 stub 最多 200,000 個 token 的上限，在建立下一個 token 前檢查，涵蓋符號、識別字、字串、heredoc 與條件指令。註解清理與字串空白處理改用文字緩衝，維持相同輸出並避免逐字或逐片段清單放大暫存記憶體。新增的兩項測試在修正前有六個失敗斷言，修正後相關的 81 個測試全部通過，並已更新 manifest。4 MiB 分號輸入現在回報 `stub token limit exceeded`，該單次解析 probe 的程序尖峰 RSS 約 55.4 MB，不能外推成完整 CLI 的記憶體硬上限。

## 安全修補評估

`docs/compatibility/security-assessments.json` 為每則安全修補記錄狀態（affected、not_affected、needs_regression、unknown）、負責的工作包與判斷依據。只看 CVE 名稱或語言不能下結論，依據必須說明對應的功能、依賴與測試。測試會檢查每份已提交的差異報告中的每個安全編號都有評估紀錄，缺一筆就失敗。

8.5.12 的 GHSA-w8hw-w9fx-j79w 與 GHSA-6wmf-4rv5-p3rp 是 Zend 在 fatal error 時用 bailout（longjmp）中止執行造成的狀態損壞。Phego 沒有共用 Zend 的 C 程式，也不使用 bailout，所以這個記憶體缺陷不會照原樣發生。PHP 看得到的部分是 fatal error 之後的執行狀態，屬於 W-14 與 W-17。8.5.12 封存檔沒有以這兩個編號命名的測試，所以狀態記為 needs_regression：要等公告細節公開、W-14 與 W-17 完成後，補上回歸測試再改狀態。

## 多版本回歸矩陣

`docs/compatibility/profile-matrix.json` 列出每個已實作的版本與整數寬度要跑的回歸測試，以及安全例外與已知缺口。目前只有 8.5.12 的 64 位元與 32 位元兩組。32 位元記錄了 `**` 與 i386 glibc 不一致的已知缺口。測試會檢查三件事：`internal/profile` 宣告已實作的版本，兩種寬度都要有項目；每組至少有一個測試套件；套件列出的 Go 測試函式都真的存在。新增版本卻沒補矩陣，或改了測試名稱沒更新矩陣，都會失敗。W-11 合併後，64 位元那組加上 HIR 的編譯錯誤對照與 Reflection／副作用對照。

## 來源驗證與回歸候選

公開入口為 `python3 tools/upstream_update.py --help`。既有 `upstream_diff.py` 保留為低階內容分類器。更新流水線使用 `upstream_update.py pair --lock LOCK OLD NEW`，先驗證兩份來源的 SHA-256，再檢查版本根目錄、必要來源檔案及封存檔資源上限。空封存檔、來源不符與缺少 parser、scanner、NEWS、stub 或 PHPT 都會失敗，不產生成功報告。

報告保留既有詳細分類，另按每個原始檔案的雜湊列出增刪與修改。C／標頭等實作、parser、原始 stub 與未分類檔案的變動標記 `needs_behavior_regression`。即使簽章沒有改變，或 stub 解析器不能解讀 `use` 別名的效果，原始變動仍會列出。這是待驗證的線索，並非已確認 PHP 行為改變。NEWS／UPGRADING 的變動保留為 `needs_assessment`，每份報告的相容狀態固定為 `not_assessed`。

新增與修改的 PHPT 會產生 `pending` 回歸候選，包含精確版本、來源封存檔雜湊、路徑、原始 PHPT 雜湊及負責工作包。候選需交由 W-04 在對應 Phego profile 執行，不能把建立候選清單算成通過回歸。刪除的 PHPT 也保留在檔案差異內，供維護者判斷舊 profile 是否繼續保留測試。

`watch BASELINE OBSERVED` 沿用 W-02 快照驗證，保留公告、tag、commit 與所有 metadata 變動。只有雙方都存在、版本或封存檔雜湊變動的系列才下載並分類，從 php.net 取得的資料也受大小、逾時與相同主機重新導向限制。`--archive-dir DIR` 只讀取以 `<sha256>.tar.xz` 命名的離線來源，不會改用附近版本或下載缺檔。單一系列失敗不會抹掉其他系列的報告。

## 整合驗收的受阻條件

- T-131／T-132 的最終負責票為 W-42。現有多版本矩陣實際只有 8.5.12，32／64 位元不算兩個版本。第二個精確版本的實作由 W-50／W-51 提供，之後才能驗證不同版本的合法差異與共用 helper 回歸。現有矩陣檢查只驗證測試名稱與覆蓋項目，不是 suite 執行證據。
- T-133／T-134 的最終負責票為 W-44。8.5.12 的安全評估維持 `needs_regression`，缺少 W-14／W-17 的 fatal-error 執行行為與對應公告的受控回歸。沒有測試的路徑不能改成 `not_affected`。
- 宣告解析與條件編譯仍只是來源分類。它不會求值平台條件，也不能代替完整 PHP 語意與真實應用驗收。

## 驗收情境與證據

這張票的局部退出條件：發現與驗證自動化可重現，不把簽章同步等同實作完成。
