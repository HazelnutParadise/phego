## 版本 profile

`internal/profile` 以精確版本、整數寬度與 `short_open_tag` 組成不可變的 profile，`Key()` 是快取與編譯產物使用的識別。`Resolve` 把要求分成三種結果：沒有記錄在[版本清冊](../compatibility/php-release-inventory.json)的版本、清冊中有但這個建置尚未實作的版本（包含第一個公開版 1.0），以及寬度不是 32 或 64 的設定。三者都不會改用相近版本。清冊仍不完整，例如目前沒有 8.4.0，所以「沒有記錄」不代表該版本不存在，錯誤訊息也這樣說明。已知版本表 `releases_gen.go` 由 `tools/profile_releases.py` 從清冊產生，`TestReleasesMatchInventory` 檢查兩者一致。目前只實作 8.5.12。

`engine.go` 用這個結果建立 Engine：未實作的版本回 `UnsupportedError`，沒有記錄的版本回欄位為 `Release` 的 `ConfigError`。`Program` 記錄編譯時的 profile，`Run` 遇到 profile 不同的程式就拒絕，`TestProgramNeverRunsUnderAnotherProfile` 模擬快取把 64 位元程式交給 32 位元 Engine 的情況。語法樹葉節點保留 token 種類，同一段 `echo 2147483648;` 在 32 位元是浮點數字面值、在 64 位元是整數字面值，`TestProfilesGiveTheirOwnResults` 檢查這個分歧。

## 版本化運算

`internal/runtime/numeric_php8512.go` 實作 PHP 8.5.12 的數字字串辨識、浮點數解析與 `precision`／shortest 兩種浮點數格式；`ops_php8512.go` 實作 `(int)`、`(float)`、`(string)`、`(bool)` 轉型，`+ - * / % **`、字串串接、位元運算、位移、`==`、`===`、大小比較與 `<=>`，含整數溢位轉浮點數、除零與位移錯誤、非數字字串的 TypeError、前導數字字串與精度流失的警告。運算回傳 PHP 會丟出的類別與訊息，警告依層級與順序記錄。這些運算目前只由測試呼叫，要等 VM 才會接上執行。

PHP 的 `**` 呼叫 C 函式庫的 `pow`。`pow.go` 是 glibc 所用 Arm optimized-routines `pow` 的 Go 翻譯（MIT 授權，見[第三方聲明](../../THIRD_PARTY_NOTICES.md)），目標是重現 arm64 上 glibc 2.41 的結果。glibc 在 arm64 以 GCC 預設的乘加融合編譯，但不是每一處都融合；哪些運算融合依 Debian glibc 2.41 libm 的反組譯確認，程式寫成明確的 `math.FMA`，其他乘積一律以 `float64()` 固定捨入，因為 Go 在 arm64 會跨敘述自動融合。Go 的 `math.Pow` 會差數個最後位數，例如 `64 ** 1.5` 會得到 511.99999999999994。

`tests/semantics/w10-ops/matrix.php` 在固定映像以 `php -n` 對 48 個運算元執行 8 種一元與 20 種二元運算，每種寬度 46464 項；`strings.php` 對 `tools/w10_numeric_strings.py` 依固定種子產生的 2 萬個字串執行 8 種轉換與比較，每種寬度 16 萬項；`pow.php` 對 `tools/w10_pow_pairs.py` 產生的 3 萬組 `pow` 輸入（含剛好落在兩個浮點數正中間的結果、接近 1、次正規數與接近溢位）比對結果位元。比對包含結果的精確編碼、丟出的類別與訊息，以及每則警告。64 位元矩陣與兩種寬度的字串語料全部一致；`pow` 語料 3 萬組、以及另一個不提交的 40 萬組語料（`--seed 7`），以 Go 的 arm64 與 amd64 建置和 arm64 PHP 比對都全部一致；`.github/workflows/semantics-ops.yml` 另在 x86-64 原生產生 amd64 PHP 的 `pow` 結果比對。32 位元 profile 的 `**` 和 PHP 不一致：linux/386 的 PHP 呼叫 i386 glibc 以 x87 指令計算的 `pow`，結果和 64 位元 glibc 不同，運算矩陣中有 51 項差 64 個最後位數以內，3 萬組 `pow` 語料在 i386 上約一半不同、最多差約 350 個最後位數。`.github/workflows/semantics-ops.yml` 在 x86-64 原生重跑兩種參考，i386 結果和 arm64 上以 QEMU 執行的結果逐位元組相同，所以這是 32 位元 profile 真實的 libm 差異，不是模擬誤差。運算矩陣測試把 51 項固定為已知缺口，數量改變就失敗；`pow` 語料只對 64 位元比對。NaN 的符號與位元樣式由 CPU 決定，比對時視為相同。另以 `FuzzNumericString` 檢查嚴格與寬鬆辨識的內部一致性（不和 PHP 對照），60 秒約 1190 萬次，找到並修正一個 32 位元繞回的邊角，修正後的值已在 PHP 8.5.12 確認：`"7000000000E+" + 0` 得到 -1589934592。[命令、雜湊與限制](evidence/W-10-operators-20261031.json)已記錄。

## 相容性檢查

`internal/compat` 掃描語法樹並回報含檔名與行號的發現，每項有種類、類別、所需能力、原始碼證據與部署影響。掃描會解析目前的命名空間、`namespace\` 前綴與 `use function` 別名，字串字面值會先解開跳脫字元，callback 字串依完整名稱判斷，`ReflectionFunction`、`Closure::fromCallable` 與 `f(...)` 視同 callback。以下寫法的目標在執行期才決定，回報為 `Unknown`，不當成可用：函式、方法、類別與 callback 由變數或運算式決定、include 路徑不是字面值或 `__DIR__` 加字面值、`eval`、可變變數、`extract`、經展開或具名參數傳入的 callback、`FILTER_CALLBACK`，以及 `php://`、`data://` 等串流包裝器的 include。需要部署授權的寫法回報為 `Capability`：字面路徑的 include、遠端 URL 的 include、shell 與行程函式（含 `mail`）、寫檔函式、寫入模式的 `fopen` 與寫檔的 `error_log`。`testdata/site.php` 與兩組表格測試涵蓋這些形式，`FuzzScan` 檢查掃描任意可解析程式都不會 panic。

局部退出條件已有證據：兩個 profile 對同一語法與運算得到各自的結果，沒有記錄與未實作的版本會被拒絕而不降級。尚未完成：

- 只有 8.5.12，沒有其他版本的 profile、語法差異或參考執行，多版本矩陣（REQ-066）尚無第二個版本。版本清冊缺少 8.4.0 等版本，需回到 W-49 補齊。
- 函式簽章、INI 預設值與擴充資料還沒有版本化。
- 物件、資源、遞增遞減、複合指定、`intdiv`、`fmod` 與字串函式的運算尚未建模，已實作的運算也尚未接上執行。
- 32 位元 profile 的 `**` 沒有重現 i386 glibc 的 x87 `pow`，非平凡的浮點數結果大多不同；要一致必須重現 x87 的計算，尚未決定是否實作。64 位元 `pow` 重現的是 arm64 glibc，amd64 glibc 在沒有 FMA 的 CPU 上走另一條路徑，結果可能不同。
- 相容掃描尚未接上函式與擴充清單，無法判斷靜態函式名稱是否存在；`static::` 與 `new static` 的晚期靜態繫結不回報；只辨識列出的 callback、行程與寫檔函式。完整驗收屬於 W-34。
